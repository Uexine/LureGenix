# LureGenix

Система развертывания и мониторинга honeytoken для серверов Linux.

Администратор выбирает сервер, тип приманки, существующий каталог и имя файла.
Backend генерирует содержимое и сохраняет задание в PostgreSQL. Агент на выбранном
Linux-сервере получает задание, создаёт файл и подтверждает фактический путь.
Статусы в интерфейсе: ожидание агента, размещён, ошибка размещения.
Пустой каталог в API или автоматический режим в форме включает выбор агентом.

## Сервер приложения

Сервисы приложения могут работать в Docker. Приманки размещает агент,
установленный непосредственно на Linux-хосте, включая основной сервер приложения.
Контейнер агента удалён из docker-compose.yml.

В корневом .env задайте параметры БД и JWT из .env.example, а также:

~~~env
OLLAMA_BASE_URL=http://ollama:11434
OLLAMA_MODEL=qwen2.5:3b
LLM_TIMEOUT_SECONDS=180
AGENT_SECRET=<случайный общий секрет серверов и агентов>
~~~

Генерация использует локальную модель в Ollama. Ключи Groq больше не используются.
Секрет агента можно сгенерировать командой:

~~~bash
openssl rand -hex 32
~~~

Не добавляйте настоящий секрет в репозиторий. Сохраните одинаковый AGENT_SECRET
в .env приложения и /etc/luregenix-agent.env каждого агента.

~~~bash
docker compose up -d --build --remove-orphans
docker compose exec ollama ollama pull qwen2.5:3b
~~~

Модель скачивается один раз и хранится в томе ollama_models. При смене
OLLAMA_MODEL загрузите соответствующую модель командой ollama pull.
Ollama работает на этом же сервере в контейнере, его API не опубликован в сеть.
Облачные возможности отключены через OLLAMA_NO_CLOUD=1. Файлы-приманки по-прежнему
размещаются агентом непосредственно в каталогах Linux-хостов.
Для установки образа и скачивания модели нужен интернет; для генерации после
скачивания внешний API не требуется. Модель использует CPU в текущей конфигурации.
Если сервер не успевает за 180 секунд, увеличьте LLM_TIMEOUT_SECONDS; при значении
выше 270 увеличьте также proxy_read_timeout в nginx/default.conf.

Интерфейс: http://10.124.21.50:8080 (локально http://localhost:8080).
Существующая авторизация сохранена; для сетевого использования настройте HTTPS.
Backend создаёт таблицу заданий при запуске. Для явного обновления существующей
БД можно также выполнить миграцию, подставив свои DB_USER и DB_NAME:

~~~bash
docker compose exec -T postgres psql -U admin -d luregenix < db/05_honeytoken_deployments.sql
~~~

Миграция добавляет таблицу и не перемещает старые файлы. Старые записи из /tokens
отмечены в интерфейсе отдельно. Создайте новые приманки для размещения агентом.

## Агент на основном или сетевом сервере

Установите Python 3, поддержку venv и systemd на целевом Linux-сервере.
На Ubuntu/Debian для venv используется пакет python3-venv.

Из копии этого репозитория на выбранном сервере выполните:

~~~bash
sudo bash agent/install.sh
sudoedit /etc/luregenix-agent.env
~~~

Укажите GATEWAY_URL приложения, одинаковый AGENT_SECRET и при необходимости
NODE_HOSTNAME и NODE_IP. Если NODE_IP пустой, агент определяет локальный IP маршрута
до приложения. Для сетевого сервера GATEWAY_URL должен быть доступен из его сети.

~~~env
GATEWAY_URL=http://10.124.21.50:8080
AGENT_SECRET=<тот же секрет, что у gateway>
AGENT_ALLOWED_DIRS=/etc,/var/www,/home,/opt
AGENT_AUTO_DIRS=/var/www/html,/var/www,/opt,/home,/etc
AGENT_STATE_FILE=/var/lib/luregenix-agent/agent.json
~~~

AGENT_ALLOWED_DIRS ограничивает размещение. AGENT_AUTO_DIRS задаёт приоритет
существующих доступных для записи каталогов. Агент не создаёт каталог приманок.
Для разных серверов эти списки можно настроить отдельно.

~~~bash
sudo systemctl restart luregenix-agent
sudo systemctl status luregenix-agent
sudo journalctl -u luregenix-agent -f
~~~

Установщик включает автозапуск, но первый запуск выполняется после настройки.
При обновлении кода повторите установку и restart. Конфигурация сохраняется.
Служба по умолчанию работает от root для доступа к /etc и другим рабочим каталогам.
Для ограниченного набора каталогов можно использовать отдельного пользователя,
предварительно предоставив ему права на каталоги размещения и файл состояния.

### Установка с основного сервера через SSH

Можно установить агент на соседний сервер с основного, если есть доступ по SSH
и sudo на целевом сервере. Кнопка удалённой установки в интерфейсе пока отсутствует.
Пример: замените admin и 10.124.21.51 на пользователя и IP целевого сервера.
Выполните из каталога репозитория на основном сервере:

~~~bash
ssh admin@10.124.21.51 'mkdir -p ~/luregenix-agent'
scp agent/agent.py agent/requirements.txt agent/install.sh agent/agent.env.example agent/luregenix-agent.service admin@10.124.21.51:~/luregenix-agent/
ssh -t admin@10.124.21.51 'sudo bash ~/luregenix-agent/install.sh'
ssh -t admin@10.124.21.51 'sudoedit /etc/luregenix-agent.env'
ssh -t admin@10.124.21.51 'sudo systemctl restart luregenix-agent'
~~~

В конфигурации удалённого агента задайте GATEWAY_URL=http://10.124.21.50:8080
и тот же AGENT_SECRET, что у приложения. Целевому серверу нужны Python 3,
python3-venv и systemd. LLM устанавливается только на сервере приложения;
на серверах с агентами модель не нужна.

## Размещение из интерфейса

1. Дождитесь появления установленного агента в списке серверов.
2. Выберите тип приманки, например SQL database backup.
3. Выберите «Выбранный каталог» и укажите существующий путь, например /var/www/html.
4. Укажите имя файла, например database_backup.sql, и нажмите «Создать и разместить».
5. В списке приманок дождитесь статуса «Размещён» и проверьте фактический путь.

В автоматическом режиме агент выбирает первый доступный каталог из AGENT_AUTO_DIRS.
Существующие файлы не перезаписываются: при совпадении имени выберите другое имя.
Отсутствующий каталог, запрещённый путь или недостаточные права показываются
как ошибка размещения. Задания для недоступного агента остаются в ожидании.

API принимает node_id, type, node_path (каталог), filename и name.
Для точного пути файла поддерживается target_kind=file.
Старое поле save_path поддерживается как путь размещения, когда node_path пустой;
оно должно содержать абсолютный Linux-путь. Новые файлы не сохраняются в /tokens.

## Генерация содержимого

SQL, dotenv, история команд, логи, конфигурация реестра, текстовые документы
и содержимое резервных архивов генерируются локально через Ollama.
Модель задаётся OLLAMA_MODEL. Если Ollama недоступна, модель не загружена
или генерация завершилась с ошибкой, задание размещения не создаётся.
Описание API: https://docs.ollama.com/api/chat.

PDF и DOCX формируются соответствующими библиотеками из текста LLM.
Архив является настоящим tar.gz с SQL-файлом. SQL никогда не исполняется:
он сохраняется как содержимое приманки.
SSH-ключи генерируются локально библиотекой cryptography, а пароли и API-ключи
генерируются secrets. Эти значения не используются для реального доступа.

## Мониторинг и реакция

Агент использует inotify для открытия, чтения, изменения, удаления и перемещения
файлов. Он отправляет события open, access, modify или delete. Они сохраняются
в event_log, поступают по WebSocket и учитываются в счётчике тревог.
Реакция в текущем варианте: журнал события и уведомление администратора;
автоматическая блокировка сервера не выполняется.

Для проверки на целевом сервере прочитайте размещённый файл:

~~~bash
sudo cat /var/www/html/database_backup.sql
~~~

В интерфейсе должно появиться событие доступа с путём файла и именем сервера.
Файлы создаются с правами 0600. Контроль применяется к существующим каталогам;
символические ссылки при создании файла не допускаются.
Нужна файловая система с поддержкой user xattr: атрибут связывает файл с заданием
и позволяет продолжить обработку после перезапуска, не перезаписывая чужой файл.

Журнал агента хранит подтверждения и очередь неотправленных событий.
При недоступности backend мониторинг ранее размещённых файлов продолжается,
а доставка повторяется после восстановления связи. При потерянном подтверждении
возможна повторная доставка события. Чтения через mmap и действия во время
остановки агента могут не попасть в inotify; PID и пользователь процесса
в текущие события не включаются.

Агенты устанавливаются администратором. Автоматическое подключение или установка
на обнаруженные в сети серверы не выполняется.

## Проверка изменений

~~~bash
python -m unittest discover -s tests -p 'test_*.py'
~~~

Для тестов нужны зависимости сервисов honeytoken_service и gateway, requests и httpx.
Тесты реального inotify выполняются на Linux и пропускаются на Windows.
